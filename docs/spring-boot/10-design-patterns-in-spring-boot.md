# Design Patterns in Spring Boot

"Name a design pattern you've used" is a weak interview question on its own — anyone can recite
the GoF list. The version that actually separates candidates is "where does Spring itself use this
pattern, and why there specifically?" This page maps the classic patterns onto the concrete Spring
APIs you already use, so the pattern names stop being trivia and become a language for describing
mechanics you've already seen elsewhere in this topic.

## Singleton — and how Spring's version differs from the GoF one

Spring's default bean scope is `singleton` (see
[Bean scopes](./02-ioc-and-dependency-injection.md#bean-scopes)): the container creates exactly one
instance of a bean and returns that same instance for every injection point and every
`getBean()` call. On the surface that's the Singleton pattern — but it's worth being precise about
how it differs from the classic GoF Singleton:

```java
// Classic GoF Singleton: enforced by the class itself
public class ConfigManager {
    private static final ConfigManager INSTANCE = new ConfigManager();
    private ConfigManager() {} // private constructor blocks any other instantiation
    public static ConfigManager getInstance() { return INSTANCE; }
}
```

```java
// Spring "singleton": enforced by the container, not the class
@Service
public class ConfigManager { // a completely ordinary, public-constructor class
    // ...
}
```

The GoF Singleton bakes uniqueness into the class itself (private constructor, static accessor) —
it's a JVM-wide guarantee, and nothing stops you from calling `new ConfigManager()` if that
constructor weren't private. Spring's singleton scope is a **container-scoped** guarantee: it's
"one instance per `ApplicationContext`," enforced by the container's bean registry, not by the
class. Nothing about `ConfigManager` itself prevents `new ConfigManager()` from creating a second,
completely separate instance outside the container — and if two `ApplicationContext`s exist in the
same JVM (unusual, but possible in some multi-module test setups), each gets its own "singleton."
This distinction — enforced by the class vs. enforced by the container — is exactly what
interviewers are checking for when they ask "is a Spring `@Service` a singleton?"

## Factory Method — `BeanFactory`, `ApplicationContext`, and `@Bean`

The Factory Method pattern delegates object creation to a method instead of calling `new` directly,
so the caller depends on an abstraction rather than a concrete constructor. The entire IoC
container is built on this: `ApplicationContext.getBean(SomeType.class)` is a factory method call —
the caller never invokes `new SomeType()` and doesn't know or care how the instance was actually
constructed. `@Bean`-annotated methods in a `@Configuration` class are literal factory methods:

```java
@Configuration
public class PaymentConfig {
    @Bean
    public PaymentGateway paymentGateway(GatewayProperties props) {
        return new StripeGateway(props.getApiKey()); // the factory method decides how to build it
    }
}
```

Every caller that gets a `PaymentGateway` injected receives whatever this method returns — they
never see the `StripeGateway` construction logic at all, which is exactly the indirection Factory
Method is meant to provide.

## Proxy — the mechanism behind `@Transactional`, `@Cacheable`, and Spring Data repositories

This one is covered in full mechanical depth in [AOP & Proxies](./06-aop-and-proxies.md), so this
is deliberately the short version: Spring wraps beans that need cross-cutting behavior in a
runtime proxy (JDK dynamic proxy or CGLIB) that intercepts calls and adds behavior — opening a
transaction, checking a cache, validating a security rule — before delegating to the real object.
Spring Data repository interfaces are proxies too, generated by a `RepositoryFactoryBean` with no
hand-written implementation class at all (see
[Spring Data JPA & Transactions](./05-spring-data-jpa-and-transactions.md)).

It's worth being able to name the distinction from **Decorator**, since they're structurally almost
identical (both wrap an object and intercept calls): Proxy's classic intent is controlling
*access* to the real object — deciding whether/when/how a call reaches it, often transparently
substituting for it — while Decorator's intent is *adding responsibilities*. Spring's AOP proxies
genuinely do both (a `@Transactional` proxy controls *when* the underlying method is allowed to
run, inside a transaction boundary — access control — while a `@Cacheable` proxy adds a
responsibility, short-circuiting the call entirely on a cache hit), which is exactly why Spring's
own documentation and most engineers just call the whole mechanism "AOP proxies" rather than
picking one GoF name over the other.

## Template Method — `JdbcTemplate`, `RestTemplate`, `TransactionTemplate`

Template Method defines the fixed skeleton of an algorithm in a base implementation, while letting
the caller plug in only the part that varies:

```java
public List<Order> findOrdersByStatus(String status) {
    return jdbcTemplate.query(
        "SELECT id, customer_id, status FROM orders WHERE status = ?",
        (rs, rowNum) -> new Order(rs.getLong("id"), rs.getString("customer_id"), rs.getString("status")),
        status
    );
}
```

`JdbcTemplate.query(...)` owns the fixed, error-prone parts of the algorithm — acquiring a
connection, preparing the statement, executing it, iterating the `ResultSet`, translating
`SQLException`s into Spring's unchecked `DataAccessException` hierarchy, and closing every
resource in a `finally` block even on failure. The only thing the caller supplies is the varying
step: the `RowMapper` lambda that turns one row into an `Order`. `RestTemplate` (and
`TransactionTemplate`, `JmsTemplate`) follow the identical shape — a `*Template` class name in
Spring is a strong signal you're looking at Template Method.

## Front Controller — `DispatcherServlet`

Front Controller centralizes all incoming requests through a single handler, which then delegates
to the specific logic for each request, instead of having many separate handlers each responsible
for their own routing/dispatch plumbing. This is exactly what `DispatcherServlet` is (full request
flow in [Spring MVC & REST](./04-spring-mvc-and-rest.md)): every HTTP request to a Spring MVC
application enters through this one servlet, which asks a `HandlerMapping` which controller method
should handle it, then dispatches to it — you never register a separate `Servlet` per endpoint the
way pre-Spring, pure-Java-EE servlet applications typically did.

## Observer — `ApplicationEventPublisher` and `@EventListener`

```java
public record OrderPlacedEvent(Long orderId, String customerId) {}

@Service
@RequiredArgsConstructor
public class OrderService {
    private final ApplicationEventPublisher publisher;

    public void placeOrder(Order order) {
        orderRepository.save(order);
        publisher.publishEvent(new OrderPlacedEvent(order.getId(), order.getCustomerId()));
    }
}

@Component
public class OrderConfirmationEmailer {
    @EventListener
    public void onOrderPlaced(OrderPlacedEvent event) {
        // send confirmation email - OrderService has no idea this listener exists
    }
}
```

`OrderService` (the subject) publishes an event with no reference to, or knowledge of, whichever
listeners (observers) react to it — `OrderConfirmationEmailer` registers itself independently via
`@EventListener`, and any number of other listeners could react to the same event without
`OrderService` changing at all. By default this is **synchronous and in-process**: the publishing
thread runs every matching listener before `publishEvent()` returns, and it's entirely
within a single JVM/`ApplicationContext` — this is the detail that most clearly separates it from
a Kafka-style event (cross-process, durable, asynchronous by nature; see
[Kafka Fundamentals](../kafka/01-fundamentals.md)). Adding `@Async` to a listener method makes that
specific listener run on a separate thread instead, without changing the publisher at all.

## Strategy — dependency injection itself

Strategy defines a family of interchangeable algorithms behind a common interface, selected at
runtime rather than hard-coded. This is arguably what dependency injection *is*, applied
systematically: a bean depends on an interface (`PasswordEncoder`, `NotificationSender`), and which
concrete implementation it gets is decided by the container — via `@Primary`, `@Qualifier`, or an
active `@Profile` (all covered in
[IoC & Dependency Injection](./02-ioc-and-dependency-injection.md#qualifier-vs-primary)) — not by
the consuming class. Swapping `BCryptPasswordEncoder` for a different encoding strategy, or an
`EmailNotificationSender` for an `SmsNotificationSender`, requires zero changes to any class that
depends on the interface, which is exactly Strategy's payoff.

## Other patterns worth recognizing

A few more show up often enough to name on sight, without needing the same depth:

| Pattern | Where it shows up in Spring |
|---|---|
| Decorator | `BeanPostProcessor` wraps a bean with added behavior without changing its source (see [Bean lifecycle](./02-ioc-and-dependency-injection.md#bean-lifecycle)) |
| Chain of Responsibility | The Spring Security filter chain — each filter decides to act and/or pass the request to the next (see [Spring Security](./07-spring-security.md)) |
| Builder | Fluent, multi-step object construction — `ResponseEntity.status(201).header(...).body(...)`, `UriComponentsBuilder`, Lombok's `@Builder` on request/response DTOs |
